# НарядAI

MVP системы выдачи и контроля производственных нарядов для кейса АО
«Костанайские минералы».

## Состав проекта

- `frontend` — Vue 3 PWA для мастера, исполнителя и руководителя;
- `backend` — FastAPI API, WebSocket и фоновые задания;
- `compose.yaml` — локальное окружение разработки.

## Быстрый запуск

1. Скопировать `.env.example` в `.env`.
2. Запустить `docker compose up --build`.
3. Открыть frontend: <http://localhost:5173>.
4. Открыть API docs: <http://localhost:8000/docs>.

Демонстрационные учётные записи:

- мастер: `master` / `1111`;
- исполнитель: `worker` / `2222`;
- электрик: `electrician` / `3333`.

Перед использованием вне локального демо обязательно замените `JWT_SECRET` в `.env`.

## Первый сквозной сценарий

1. Мастер входит по логину и PIN-коду.
2. Создаёт и выдаёт наряд исполнителю.
3. Исполнитель принимает наряд и начинает выполнение.
4. Мастер видит изменение статуса по WebSocket.
5. Каждое действие сохраняется в журнале событий.

## Проверка интерфейса

В шапке и на экране входа доступен выбор оформления: светлое, тёмное или
«Как в системе». Выбор сохраняется в браузере отдельно от сессии пользователя;
системный режим реагирует на изменение темы ОС. Цвета интерфейса находятся в
`frontend/src/theme.css`.

В каталоге `frontend`:

```sh
npm test
npm run build
```

Компонентные тесты проверяют канбан на широком и узком экране, состояния
загрузки/ошибок, действия исполнителя и регистрацию Quasar-компонентов.
Это не браузерные E2E-тесты и не проверка внешнего вида.

Ручная приёмка в двух отдельных сессиях браузера:

1. Войти мастером; проверить показатели, исполнителей и фильтры нарядов.
2. На ширине 390 px переключить колонки канбана; карточки и кнопки не должны
   требовать горизонтального скролла страницы.
3. Войти исполнителем; открыть «Отчёт и фото», проверить фотографии до ремонта.
4. При медленной загрузке фото текст отчёта и хронология должны быть доступны
   сразу; ошибка отдельного фото не должна скрывать весь отчёт.
5. В уже открытой сессии отключить сеть, выполнить действие исполнителя,
   восстановить сеть и проверить синхронизацию. Офлайн-вход после перезагрузки
   страницы пока не поддерживается.
6. Проверить выдачу, принятие, начало и завершение наряда с фото; отдельно
   проверить пустой список и недоступность API.

Текущий UI-этап не меняет локальную LLM: её подключение и настройка отложены.

## Отдельный эксперимент с изображениями

VLM-проба не подключена к нарядам, не меняет оценки и не закрывает работы.
Используется Qwen2.5-VL-3B-Instruct Q4_K_M с совместимым визуальным модулем
Q8_0 из репозитория `ggml-org/Qwen2.5-VL-3B-Instruct-GGUF`.
Веса находятся в игнорируемом Git каталоге `.local-models/vlm` (около 2,8 ГБ).

Запуск из корня проекта в отдельном терминале:

```sh
bash scripts/run_vlm_probe.sh
```

Сервер слушает только `127.0.0.1:8081`, обрабатывает один запрос за раз,
контекст ограничен 4096 токенами, изображение — 1024 визуальными токенами.
Основной текстовый сервер на порту 8080 и `.env` не изменяются.
Не запускайте обе модели одновременно, если не хватает VRAM.

Проверка одного изображения или пары до/после во втором терминале:

```sh
python scripts/vlm_probe.py /absolute/path/before.jpg /absolute/path/after.jpg \
  --task 'Первое фото до, второе после ремонта редуктора. Опиши видимые изменения и ограничения осмотра. Не утверждай, что ремонт успешен.'
```

Скрипт передаёт изображения только локальному серверу и выводит JSON и время
ответа. `needs_human_review` всегда `true`. Ответ модели не является
доказательством исправности или безопасности. Ограничение разрешения может
скрывать мелкие дефекты; пригодность проверяется на размеченных реальных фото.
Остановить сервер и освободить GPU: Ctrl+C в его терминале.

Техническая проба 07.10.2026: RTX 4050 Laptop 6 ГБ, llama.cpp build 11146.
После загрузки сервера `nvidia-smi` показал 4054 МБ общей занятой VRAM
(до запуска 182 МБ); после запроса — 4217 МБ. Пиковое потребление не измерялось.
На скриншоте интерфейса получен завершённый JSON с верно
прочитанным заголовком «Результаты смены»: 2,78 с, 1174 входных и 128 выходных
токенов; 67 входных токенов были закэшированы. Это проверка запуска и обработки
изображения, не оценка распознавания дефектов или качества ремонта.
Оборванный по лимиту ответ отвергается, даже если содержит корректный JSON.

Тесты клиента: `python -m unittest discover -s scripts -p 'test_vlm_probe.py'`.

### Проба на VisA (07.10.2026)

Источник: [Amazon Science VisA / SPot-the-Difference](https://github.com/amazon-science/spot-diff),
CC BY 4.0. Авторы: Yang Zou, Jongheon Jeong, Latha Pemula, Dongqing Zhang,
Onkar Dabeer. Взяты первые три аномальных и три нормальных изображения категории
`candle` по порядку официального tar-архива. Это предварительная выборка,
не репрезентативный тест промышленного оборудования и не пары до/после ремонта.
Разметка проверяемых фото, маски и исходные имена не передаются модели.

```sh
python scripts/visa_sample.py
bash scripts/run_vlm_probe.sh
# Во втором терминале, из корня проекта:
python scripts/visa_benchmark.py
python scripts/visa_benchmark.py --reference sample-04.JPG
python scripts/visa_benchmark.py --visual-only
python -m unittest discover -s scripts -p 'test_*.py'
```

Загрузчик использует HTTP Range: передано около 7,1 МиБ вместо полного архива
1,93 ГБ. Файлы, SHA-256 и происхождение находятся в
`.local-models/datasets/visa-sample/manifest.json`.
Сырые ответы и HTML-галереи сохраняются отдельно для каждого режима.

| Проба | Тестовых фото | Найдено аномалий | Верно признано нормальными | Неопределённых | Медиана ответа |
| --- | ---: | ---: | ---: | ---: | ---: |
| Без эталона | 6 | 0 | 0 | 6 | 2,59 с |
| Эталон + уточнённый запрос | 5 | 0 | 0 | 5 | 3,02 с |
| Узкий запрос о видимых повреждениях | 6 | 1 | 0 | 5 | 2,43 с |

Во второй пробе нормальный `sample-04.JPG` используется как эталон и исключён
из оценки. В третьей пробе уточнено, что обычный фитиль не является дефектом,
а неизвестная функциональность не препятствует визуальному осмотру. Это
эксперименты с запросами на тех же данных, не независимая оценка качества.
Параметры: Qwen2.5-VL-3B Q4_K_M, mmproj Q8_0, 1024 визуальных токена на фото,
4096 контекст, temperature=0, seed=42. Все 17 ответов — завершённый JSON.

Вывод: в этой конфигурации модель не годится для автоматического подтверждения
ремонта. Она часто воздерживается от решения, путает фитили с повреждениями,
а в текстовых наблюдениях на нормальных фото выдумывает дефекты. Ноль
формальных false alarms не означает отсутствия ложных замечаний: счётчик
учитывает поле decision, а не достоверность текста. Неопределённые ответы
не считаются правильными. После первой пробы занято 4101 МиБ общей VRAM;
пиковое потребление и потребление второй/третьей проб не измерены.
До подключения к MVP нужна более широкая независимая выборка, ручная проверка
описаний/локализации и проверка влияния разрешения, запросов и модели.

### Сравнение разрешения (07.10.2026)

Повторены те же шесть фото с неизменным узким запросом и отдельным холодным
запуском сервера для каждого лимита. Обе пробы: temperature=0, seed=42,
900 выходных токенов, контекст 4096, одна сессия. Меняется только
`--image-max-tokens`. Общая GPU-память опрашивается примерно раз в 0,5 с;
это максимальный наблюдавшийся замер, не гарантированный пик и не память
только модели. Фоновые процессы GPU входят в цифры.

| Лимит визуальных токенов | Отмечено дефектных фото из 3 | Нормальных признано нормальными из 3 | Неопределённых из 6 | Медиана ответа | Макс. замер общей VRAM |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1024 | 1 | 0 | 5 | 2,42 с | 4245 МиБ |
| 2048 | 2 | 0 | 4 | 4,02 с | 4282 МиБ |

Входной запрос действительно увеличился: 1281 → 2223 токена по данным API.
На этих фото увеличение лимита дало одно дополнительное совпадение decision
с разметкой, но не устранило выдуманные повреждения на нормальных снимках и
ошибки локализации. Это один прогон на уже использованной маленькой выборке,
не основание объявлять повышение общей точности или статистическую значимость.
Для MVP автоматическое подтверждение по-прежнему неприемлемо.

Повторить (указать новое имя, чтобы не перезаписать результаты):

```sh
VLM_IMAGE_MAX_TOKENS=2048 bash scripts/run_vlm_probe.sh
# Во втором терминале:
python scripts/visa_benchmark.py --visual-only --run-name my-resolution-2048 --monitor-gpu
```

Результаты: `.local-models/datasets/visa-sample/resolution-2048-results.json`
и `resolution-1024-control-results.json`; рядом HTML-галереи обоих прогонов.
Дальнейшее сравнение моделей должно включать независимую выборку и проверку
достоверности текстовых наблюдений, а не только совпадения поля decision.

заметила красное пятно, но отвергла его как дефект; оба anomaly признала
не имеющими видимых дефектов. Ни один результат не доказывает пригодность
для приёмки ремонта. Нулевой счётчик false_alarms не означает отсутствие
выдуманных наблюдений.

Первый запуск старой модели при открытой игре закончился CUDA out-of-memory
и падением сервера; неуспешный результат `qwen25-3b-results.json` сохранён,

текстовая модель не менялись.

достоверности локализации. При интеграции — только черновые наблюдения
с обязательной проверкой человеком, без изменения статуса наряда.

### Первый пилот на оборудовании: видимые следы жидкости

Предложенный узкий сценарий — корпус насоса или редуктора. Проверяем только
видимые следы жидкости, не определяем её состав, активность утечки,
исправность агрегата и успешность ремонта. Сценарий ещё требует согласования
со специалистом и реальных фото; свечи VisA не заменяют такую проверку.

Метки для ручной разметки:

- `visible_trace` — специалист отмечает видимый след и его положение;
- `no_visible_trace` — нужная поверхность видна, следов не обнаружено;
  это не утверждение, что агрегат сухой со всех сторон или исправен;
- `unassessable` — поверхность скрыта, кадр размыт либо по фото нельзя
  отличить след жидкости от грязи/тени. Причина обязательна в `visible_evidence`.

Нужны не только явные следы, но и отрицательные примеры: тени, грязь,
ржавчина, блики, очищенная поверхность. Разметку даёт человек, не проверяемая
модель. До/после одного ремонта, соседние кадры и один агрегат остаются в
одном разделе набора. `development` нужен для настройки запроса,
`evaluation` — для проверки после фиксации запроса. Проверочные ответы
не используются для настройки и повторного объявления улучшения на тех же фото.

Шаблон: `experiments/equipment-photo-pilot.example.json`. Положить его копию
как `manifest.json` рядом с фотографиями в игнорируемый каталог
`.local-models/datasets/equipment-pilot/`, затем заполнить `samples`:

```json
{
  "file": "photos/pump-01.jpg",
  "sha256": "полный SHA-256 файла, вычисленный sha256sum",
  "equipment_id": "pump-01",
  "capture_session": "pump-01-session-01",
  "reviewer": "псевдоним специалиста",
  "label": "visible_trace",
  "split": "evaluation",
  "visible_evidence": "видимый след на левой стороне корпуса; состав неизвестен",
  "source": "собственное фото с разрешением владельца",
  "usage_permission": "описание разрешения на локальное использование"
}
```

Пример показывает структуру, не является настоящей разметкой. Избегать лиц,
персональных данных и конфиденциальных надписей; разрешение на фотографии
получить до использования. Кадры снимать только в разрешённых безопасных
условиях, не приближаться к работающему оборудованию ради эксперимента.

Проверка без запуска GPU/модели и без сетевых запросов:

```sh
python scripts/equipment_dataset.py .local-models/datasets/equipment-pilot/manifest.json
python -m unittest discover -s scripts -p 'test_*.py'
```

Проверяются обязательные поля, размер/сигнатура файлов, SHA-256, точные
дубликаты и пересечение агрегатов/сессий между разделами. Это не полноценное
декодирование изображения, не поиск похожих кадров и не проверка истинности
разметки/разрешений. Пустой шаблон отклоняется; отсутствие одного из двух
оцениваемых классов отмечается предупреждением. Размер набора и доли классов
нужно выбирать под реальный процесс; маленькая проба не подтверждает надёжность.

После сбора фото — отдельный прогон по этому сценарию (`--scenario liquid-trace`),
а не candle-запросом из `visa_benchmark.py`. Учитывать пропуски следов, ложные тревоги, uncertain,
ошибки JSON и достоверность локализации. На `unassessable` отдельно считать
случаи уверенных ответов. Ни одна метрика пока не меняет статус наряда.

Реальных фотографий у пользователя пока нет. Найден кандидат для отдельного
синтетического эксперимента: [Oil leak dataset, версия 1](https://data.mendeley.com/datasets/nbxzxn3ffk/1),
DOI `10.17632/nbxzxn3ffk.1`, авторы Matteo Cardoni, Danilo Pau,
Laura Falaschetti, Claudio Turchetti, Marco Lattuada, лицензия CC BY 4.0.
По описанию авторов это 3D-рендеры соединения вала и кронштейна генератора
ветротурбины, со следами масла и без них. Скачана только небольшая исходная
выборка, описанная ниже. Не считать её фотографиями насосов или независимой
проверкой на настоящем оборудовании. При будущем разделении набора отделять
варианты одного рендера от проверочных групп и сохранять авторство/источник.

## Очередь офлайн-действий

- Запись считается сохранённой только после завершения транзакции IndexedDB.
- Очередь привязана к пользователю, отправляется по порядку ID и останавливается
  при смене сессии. Для нескольких вкладок используется Web Locks, если браузер
  поддерживает их на текущем origin; без них защита действует в пределах вкладки.
- Обрыв сети, `401` и ошибки сервера оставляют действия в очереди. Повторная
  попытка выполняется при восстановлении сети/WebSocket, раз в 15 секунд при
  наличии очереди или кнопкой «Отправить».
- Ошибки `400/403/404/409/422` помечают действие как конфликтное, но не удаляют
  отчёт и фото. Последующие действия по этому наряду ждут разбора; другие наряды
  продолжают синхронизироваться. Панель «На устройстве» показывает причину ошибки
  и позволяет повторить отправку после проверки статуса наряда.
- До подтверждения сервера интерфейс показывает локальный ожидаемый статус.
  Очередь не заменяет серверную историю и не обеспечивает офлайн-вход.

### Идемпотентность синхронизации (08.10.2026)

Переходы статуса и отправка отчёта теперь сначала сохраняются в IndexedDB
с UUID действия, включая онлайн-режим. Только после фиксации локальной
транзакции очередь отправляет `Idempotency-Key`. При обрыве ответа или
неудачном удалении подтверждённой записи следующая попытка использует тот
же ключ. Старые записи очереди без ключа получают его с сохранением до
первой отправки новым клиентом; это не восстанавливает результаты запросов,
отправленных старой версией без ключа.

Миграция `0008_idempotency` добавляет `idempotent_actions`. Уникальность —
по авторизованному пользователю и ключу; автор не берётся из payload.
PostgreSQL transaction advisory lock сериализует конкурентные повторы,
а блокировка наряда сохраняет обычную проверку переходов. Успешный ответ,
событие, статус, отчёт и списания материалов фиксируются одной транзакцией.
Повтор возвращает исходный снимок ответа, не выполняет действие заново и
не создаёт повторного broadcast. Доступ к наряду и роль проверяются и при
повторе; это не обход авторизации. После синхронизации UI перечитывает
текущее состояние, поскольку наряд мог измениться после исходного ответа.

Повторное использование ключа с другим endpoint, нарядом или содержимым
возвращает `409`. Для multipart в отпечаток входят поля, точная строка
`materials_json`, имя/тип фото и SHA-256 его содержимого, а не случайный
multipart boundary. Не менять данные сохранённого действия при повторе.
Ошибки валидации и откаты не фиксируют успешный receipt. Заголовок остаётся
необязательным для совместимости со старыми клиентами, но без него гарантии
дедупликации нет. Создание нарядов и AI-review пока этим механизмом не покрыты.

Файловое хранилище не является частью транзакции PostgreSQL: после аварийного
завершения процесса до commit возможен лишний файл без строки в БД. Очистка
таких файлов — отдельная задача; не называть систему глобальной exactly-once.
Receipts пока не удаляются автоматически: срок хранения следует согласовать
до длительного использования, чтобы не нарушить поздние офлайн-повторы.

Проверено на отдельном временном PostgreSQL 17, не на рабочей базе:

- полный путь миграций до `0008_idempotency`, `alembic current` и startup-логи;
- 8 HTTP/DB интеграционных тестов: потеря ответа после commit, повтор после
  следующего перехода, конкурентные переходы и отчёты, неизменное число
  фото/материалов/событий, изменённое содержимое, 401/403 и откат;
- 30 фронтенд-тестов в существующем образе frontend, включая стабильный ключ,
  ошибку сохранения ключа, ошибку удаления записи и JSON/multipart headers;

  `frontend/dist/sw.js` принадлежит другому владельцу и недоступен для записи;

### Доработка и история отчётов

Миграция `0009_completion_history` снимает ограничение «один отчёт на наряд».
Каждая новая сдача создаёт отдельную запись с материалами; фото после ремонта
и автоматическая проверка привязаны к этой записи. Старые данные сохраняются:
миграция связывает существующие фото «после» и оценки с прежним отчётом.
Фото «до» остаются общими для наряда. Откат миграции запрещён, если уже есть
несколько отчётов/оценок на наряд: история не удаляется ради downgrade.

В окне «Отчёт» можно выбрать версию: текст, материалы и фото меняются вместе.
Автоматическая оценка показывается для последней версии; прежние оценки
сохраняются в БД. Список оценок и рейтинг используют только последнюю сдачу,
а не случайную предыдущую. Повторная отправка с прежним `Idempotency-Key`
не создаёт новую версию и не откатывает состояние закрытого наряда.

Мастер может принять либо вернуть исполненный наряд **без запуска ИИ**.
При возврате обязательно конкретное замечание (не пустая строка/пробелы),
при закрытии требуется подтверждение в интерфейсе. Исполнитель возобновляет
работу из состояния «На доработке» и сдаёт новый отчёт. Замечание мастера
сохраняется в хронологии. ИИ не принимает решение за мастера.

Проверено 08.10.2026, только в одноразовых тестовых БД:

- 10 HTTP/DB интеграционных тестов, включая два отчёта, новую проверку,
  отсутствие старой оценки в текущем списке, закрытие, повтор первого запроса
  после закрытия и запрет закрытия исполнителем;
- переход `0008 → 0009` с существующим отчётом, фото и оценкой: данные
  сохранены, обе новые связи заполнены;
- 31 frontend-тест, TypeScript и production PWA build;
- в браузере: переключение версий, заблокированный возврат без замечания,
  сохранение замечания и состояние «На доработке», ручное закрытие без ИИ;
  у отчёта осталась одна прокручиваемая область вместо двух.

### VLM в MVP: визуальные наблюдения, не приёмка

Зафиксирована **Qwen3-VL-4B-Instruct Q4_K_M + F16 mmproj**, без обучения.
В окне отчёта мастер/администратор может запустить анализ последней сдачи.
Берётся последнее фото «после» этой версии и, если есть, первое фото «до»
наряда. Это максимум два снимка; использованные ID сохраняются и показаны
в интерфейсе. Текст задания, комментарии, исходные имена и разметка датасета
модели не передаются. JPEG/PNG/WebP проверяются по сигнатуре, размер — до
10 МБ на файл; проверка сигнатуры не заменяет полное декодирование изображения.

Миграция `0010_photo_observations` добавляет отдельные наблюдения с привязкой
к версии отчёта, именем модели, версией запроса, фото, временем и ошибкой.
Статусы: `running`, `done`, `failed`. Повтор готового анализа возвращает
сохранённый результат, не запускает GPU заново. Ошибку можно повторить.
Старая версия сохраняет свои наблюдения, новая не наследует их.
Результат никогда не меняет статус наряда, оценку или рейтинг; Vue выводит
текст, а не HTML модели. Обязательное предупреждение о проверке человеком
задаёт приложение, независимо от ответа модели.

Это **не фоновая очередь задач**: POST ждёт инференс, а состояние `running`
сохраняется перед обращением к модели. После перезагрузки отчёта состояние
читается из БД. Кнопка проверки статуса возвращает текущую попытку; если
процесс оборвался, повтор разрешён после `VLM_TIMEOUT_SECONDS + 30` секунд.
UUID попытки защищает от записи запоздавшего результата поверх новой попытки.
GPU-lock рассчитан на **один backend-процесс**: другой наряд получает 429,
не помещается в скрытую очередь. Для нескольких workers/серверов нужен общий
worker/очередь с ограничением параллельности, а не увеличение числа Uvicorn workers.

Настройки: `VLM_ENABLED` (по умолчанию false), `VLM_BASE_URL`,
`VLM_MODEL=NaryadAI-Qwen3-VL-4B`, `VLM_TIMEOUT_SECONDS=90`, `VLM_API_KEY`.
Текстовая LLM на 8080 не заменяется. Не держать обе модели на GPU 6 ГиБ
одновременно без отдельного измерения памяти. URL допускает только loopback,
`host.docker.internal` или частный IP; внешние облачные адреса отклоняются.

Локальный запуск VLM:

```sh
bash scripts/run_qwen3_vlm_probe.sh
```

Скрипт по умолчанию слушает только `127.0.0.1:8081`. Для backend на хосте
использовать `VLM_BASE_URL=http://127.0.0.1:8081`.
**Контейнер Compose не может подключиться к host loopback через
host.docker.internal.** Для такого запуска оператор должен выбрать доступный
частный адрес Docker bridge в `VLM_HOST` и задать одинаковый случайный
`VLM_API_KEY` для скрипта и backend. Скрипт отказывается слушать вне loopback
без ключа; не открывать порт в Интернет. Адрес gateway можно узнать командой
`docker network inspect bridge`. Backend использует Bearer-ключ, llama-server
получает его через `LLAMA_API_KEY`, без ключа в аргументах процесса.
После настройки `.env`: `docker compose up --build`. Рабочая `.env` в ходе
проверки не менялась; VLM автоматически не включается.

### PWA и приёмка на телефоне

Команды `dev`, `build`, `preview` явно используют `vite.config.ts`:
в checkout есть старый сгенерированный `vite.config.js`, который иначе
затеняет TS-конфигурацию. Старый файл не удалён. Manifest содержит постоянный
ID, scope/start URL, PNG 192/512 и maskable-иконку; добавлены favicon и
apple-touch-icon. Генерация иконок: из `frontend` выполнить
`npx pwa-assets-generator --preset minimal public/app-icon.svg`.

Service worker кэширует оболочку, иконки и локальные шрифты. API, защищённые
фото и данные пользователей не добавляются в его runtime cache; навигация
`/api/*` исключена из SPA fallback. Обновление предлагается кнопкой, а не
перезагружает страницу автоматически. Открытые формы/отчёт и активные действия
блокируют обновление; активация SW из другой вкладки не должна автоматически
сбрасывать форму текущей вкладки. Сам механизм обновления не сохраняет поля:
для формы сдачи отчёта отдельно добавлен черновик (см. ниже), но форма создания
наряда по-прежнему теряется при ручной перезагрузке.

При холодном запуске без доступа к API сохранённый токен больше не удаляется
из-за сетевой ошибки/5xx. Показывается сообщение и повтор проверки соединения;
после возврата сети вход подтверждается сервером, затем запускается очередь.
Истёкшая/отклонённая сессия требует нового входа. Поздний ответ не восстанавливает
пользователя после выхода или смены токена. Это **не офлайн-авторизация**:
после холодного запуска без сети наряды недоступны до серверной проверки.
В уже открытой подтверждённой сессии можно сохранять действия и отчёт в
IndexedDB; сохранённая очередь не удаляется при выходе.

Установка и service worker требуют доверенного HTTPS, кроме localhost на
самом устройстве. Обычный `http://IP-компьютера:5173` на телефоне не заменяет
HTTPS. Не обходить предупреждения сертификата и не публиковать тестовый
контур в Интернет ради проверки. Устанавливать **production build**, не
Vite dev-сервер: `npm run build`, затем локальная раздача/HTTPS reverse proxy.
Frontend API/WS URL должны быть доступны с телефона (`localhost` на телефоне
означает телефон, не ноутбук; для HTTPS-страницы нужны HTTPS/WSS endpoints).
Текущий CORS backend допускает только localhost:5173: для выбранного
телефонного HTTPS-origin потребуется точечная настройка CORS, не `*`.

Проверено 08.10.2026: 37 frontend-тестов и TypeScript/production build;
сгенерированные manifest/SW содержат иконки, шрифты, обновление по сообщению

В браузере production-сборка при выключенном API показала сохранённую сессию
и повтор подключения вместо сброса токена. Это **не проверка авиарежима,
установки на телефон или реального обновления двух вкладок**.

Ручная приёмка на настоящем телефоне, когда есть доверенный HTTPS-контур:

1. Открыть production URL, войти исполнителем, загрузить наряды/справочники,
   установить приложение из меню браузера и один раз открыть онлайн.
2. В открытом приложении включить авиарежим, заполнить отчёт с фото и нажать
   сдачу. Убедиться, что очередь показывает сохранённый текст и число фото.
3. Закрыть и открыть PWA без сети: оболочка открывается, вход требует сеть;
   это ожидаемое ограничение MVP, не обещание офлайн-доступа к нарядам.
4. Вернуть сеть, подтвердить/восстановить вход той же учётной записью.
   Очередь должна очиститься; проверить единственный отчёт, фото и событие.
5. Повторить с истёкшей сессией: нужен вход; очередь сохраняется и не
   отправляется при входе другой учётной записью.
6. Выпустить новую сборку при открытой форме в двух вкладках: обновление
   текущей вкладки заблокировано; обновление другой не стирает форму.
7. Проверить размеры и поворот экрана, выбор фото/камеру, клавиатуру и

### Изолированный HTTPS-стенд для телефона

`compose.https.yaml` запускается **самостоятельно**, не как override основного
Compose. Проект `naryadai-phone` имеет собственные тома БД и фото, production
frontend в Nginx и миграции backend без autoreload. LLM/VLM выключены. База/API
не имеют опубликованных портов. Снаружи доступен только HTTPS; по умолчанию
он привязан к `127.0.0.1:8443`, пока вы явно не выберете LAN-IP ноутбука.
Это локальный демо-контур со стандартными PIN, **не публичный production**.

API `/api/*` и WebSocket `/api/ws` проксируются через тот же адрес. Сборка
задаёт пустые `VITE_API_URL`/`VITE_WS_URL`: API использует относительный путь,
WS — протокол и host страницы, включая порт. Неопределённые переменные в
обычном dev-режиме по-прежнему используют localhost:8000. CORS расширять
не требуется: запросы same-origin. Конфигурация Upgrade/Connection следует
[официальному примеру Nginx](https://nginx.org/en/docs/http/websocket.html).
API получает `Cache-Control: no-store`, shell/SW/manifest — `no-cache`.
HTTP access logs выключены, Uvicorn ограничен warning: даже при
`--no-access-log` его INFO-лог WebSocket может содержать токен из URL.

Подготовка выполняется вручную; корневой сертификат в систему/телефон
автоматически не устанавливается:

1. Скопировать `.env.https.example` в `.env.https`. Для `PHONE_DB_PASSWORD`
   и `PHONE_JWT_SECRET` получить **два разных** значения `openssl rand -hex 32`.
   Не использовать тестовые/рабочие секреты и не менять пароль уже созданной
   БД простым редактированием env — её пользователь сохранит старый пароль.
2. Выбрать текущий частный IPv4 ноутбука в вашей доверенной Wi-Fi сети.
   Телефон должен быть в той же сети, без client isolation. Вписать его в
   `PHONE_BIND_IP`; не ставить `0.0.0.0` и не делать проброс порта в Интернет.
3. Установить `mkcert`, создать сертификат для **этого же IP**. Пример ниже
   использует условный `192.168.1.114`: заменить его своим актуальным IP.

```sh
mkdir -p /home/nekit/NaryadAI/.local-certs/phone
mkcert -cert-file /home/nekit/NaryadAI/.local-certs/phone/certificate.pem -key-file /home/nekit/NaryadAI/.local-certs/phone/key.pem localhost 127.0.0.1 192.168.1.114
chmod 600 /home/nekit/NaryadAI/.local-certs/phone/key.pem
```

4. `HTTPS_CERT_DIR` должен указывать на абсолютный каталог только с
   `certificate.pem` и `key.pem`. В него **не копировать `rootCA-key.pem`**.
   Для доверия на телефоне нужен только публичный `rootCA.pem` из каталога,
   который показывает `mkcert -CAROOT`. Установить его вручную как CA по
   инструкции вашего Android/iOS; на iOS дополнительно включить полное
   доверие. [Документация mkcert](https://github.com/FiloSottile/mkcert#mobile-devices)
   описывает этот шаг. Установка CA расширяет доверие устройства: храните
   ключ CA приватно и удалите тестовый CA с телефона после эксперимента.
   Не обходить предупреждение сертификата в браузере.
5. Проверить конфигурацию и запустить **отдельный** проект из корня репозитория:

```sh
docker compose --env-file .env.https -f compose.https.yaml config --quiet
docker compose --env-file .env.https -f compose.https.yaml up -d --build
docker compose --env-file .env.https -f compose.https.yaml exec -T backend alembic current
```

Ожидается `0010_photo_observations (head)`. На телефоне открыть
`https://ВАШ-LAN-IP:8443` без предупреждений TLS, войти демо-пользователем
и пройти чек-лист выше. Нужен доступ к порту 8443 через локальный firewall;
его автоматического изменения нет. При смене IP пересоздать сертификат,
обновить bind и URL. Новый origin имеет отдельную сессию/IndexedDB-очередь —
нельзя менять адрес с неотправленными действиями и ожидать переноса очереди.

Остановить стенд: `docker compose --env-file .env.https -f compose.https.yaml down`.
Без `-v`: БД и фото сохраняются. Обновление frontend — тот же `up -d --build`;
далее проверка предложения обновления в PWA. `.env.https` и `.local-certs/`
исключены из Git; `.env*` также исключены из build context обоих приложений.

### Черновики отчётов исполнителя

Форма сдачи сохраняет работы, шифр неисправности, комментарий, добавленные
материалы, незавершённый выбор материала/количества и выбранное фото в
IndexedDB. Ключ — пользователь + наряд, данные остаются только на текущем
устройстве и origin. Вход другого пользователя не показывает чужой черновик;
выход не удаляет черновики. Это разграничение интерфейса, не шифрование
локального хранилища: на общих устройствах не считать его защищённым сейфом.

Сохранение происходит при изменении полей; надпись «сохранён» появляется
после commit транзакции, не после одного IDB request. При закрытии/сдаче форма
ждёт завершения записей. Пока сохранение идёт или есть ошибка, обычная
перезагрузка запрашивает предупреждение браузера (на мобильных принудительных
закрытиях гарантии нет). При отказе/quota хранилища ошибка видна, поля остаются
в форме; закрытие требует подтверждения потери несохранённых полей. При
одновременном редактировании двух вкладок проверка revision запрещает
молча перезаписывать более новый черновик: нужно скопировать свои поля и
разобрать конфликт вручную, авто-слияния нет.

Сдача ждёт записи черновика, затем одной транзакцией добавляет отчёт/фото в
очередь и удаляет только совпадающую revision черновика. Abort оставляет
черновик и не добавляет отчёт. Более новый чужой revision не удаляется.
Сетевой сбой после commit не приглашает повторно сдать отчёт: он уже в
очереди со стабильным idempotency key. Конфликт сервера тоже сохраняется в
очереди, не маскируется как потерянная форма. После успешного переноса
повторное открытие формы пустое; сохранённый отчёт искать в очереди.

DB `naryad-ai` обновлена с версии 1 до 2 с новым store `completion-drafts`,
старая очередь не удаляется. Если старая вкладка блокирует обновление,
приложение предлагает закрыть её. Черновик восстанавливается после онлайн
подтверждения входа и открытия нужного наряда — холодный офлайн-доступ к
нарядам по-прежнему не реализован. Автоочистки по сроку и кнопки удаления
черновика пока нет; форма создания наряда также пока без черновика.

Текст формы исправлен: отчёт сдаётся мастеру; AI, если включён и отдельно
запущен мастером, даёт рекомендации, но не принимает работы автоматически.

Проверено 08.10.2026: 46 frontend-тестов и TypeScript/production Docker build.
Тестовый transaction adapter проверяет user/order isolation, stale revision,
атомарный перенос/abort и сохранение более нового черновика. В отдельной
браузерной форме с настоящим IndexedDB проверяется восстановление текста,
комментария и JPEG после перезагрузки, изоляция пользователя, перенос в
очередь и отказ перезаписи из устаревшей второй вкладки. Закрытие формы при

серверная/телефонная приёмка.

### Проверка загружаемых фотографий

Реализована 08.10.2026 для фото создания наряда и отчёта исполнителя.
Backend принимает только статические JPEG, PNG и WebP: до 10 МиБ на файл,
до 24 000 000 пикселей и до 8192 пикселей по каждой стороне. При создании
наряда — максимум 5 фото и 25 МиБ суммарно. HTTPS nginx допускает запрос
до 26 МиБ с учётом multipart/JSON; это не увеличивает лимит самих фотографий.
Фронтенд ограничивает выбор форматов/размера и показывает подсказки, но
окончательная проверка всегда на сервере.

`backend/app/photos.py` определяет фактический формат, проверяет размеры,
анимацию и соответствие заявленного MIME. Пустой MIME или
`application/octet-stream` допускаются, если содержимое действительно
поддерживается. MIME и расширение сохраняемого UUID-файла берутся из
декодированного изображения, а не пользовательского имени. Проверка
`verify()` дополнена повторным открытием и полным `load()`: одно чтение
заголовка не гарантирует декодируемость изображения
([документация Pillow](https://pillow.readthedocs.io/en/stable/reference/Image.html)).
Все фотографии пакета проверяются до создания наряда и файлов. Новый
невалидный отчёт не создаёт completion, фото или квитанцию действия.

Оригинальные байты сохраняются без перекодирования: EXIF/метаданные не
очищаются. SVG, GIF, HEIC, анимация и повреждённые изображения отклоняются;
для HEIC нужно предварительное преобразование. Декодирование вынесено из
event loop в пул с двумя потоками на процесс. Это ограничение параллельных
декодирований, **не** изолированная песочница, антивирус или полный лимит
памяти/времени/очереди запросов. Собственная защита Pillow от чрезмерного
числа пикселей также не отключается.

Повтор уже подтверждённого действия возвращает сохранённую квитанцию до
нового декодирования, чтобы сохранить совместимость со старыми отчётами.
Это не позволяет загрузить новый невалидный файл. Существующие фотографии
не пересканируются; старые неподдерживаемые MIME (например, SVG) при выдаче
возвращают 415, но запись и файл не удаляются. Поддерживаемые фотографии
отдаются с `X-Content-Type-Options: nosniff` и прежними проверками доступа.

Offline-очередь считает 413/415/422 постоянными ошибками: отчёт и фото
сохраняются в конфликтной записи без бесконечных повторов. Редактор фото
внутри такой записи ещё не реализован; автоматической замены/сжатия нет.

Проверено: 7 тестов декодера, 19 HTTP/PostgreSQL тестов workflow/idempotency,
6 тестов VLM-клиента, 47 тестов фронтенда и production-сборка Vue/PWA.
Использовалась отдельная временная БД с миграциями до `0010`; рабочая БД
не изменялась. Новый браузерный/телефонный приёмочный прогон не проводился.
Добавлена зависимость Pillow 12.3; для применения нужен rebuild backend
и frontend, новой миграции нет:

```sh
docker compose up -d --build backend frontend
```

Для отдельного HTTPS-стека используйте его compose-файл и env по разделу
выше, не объединяйте его с dev-compose. Следующий приоритет — ограничение
перебора PIN; затем исправление конфликтных фото из offline-очереди.
